# Sampath Food City

**A full-stack online grocery store with a back-office management system.**
React + TypeScript on the front, NestJS + PostgreSQL behind it, JWT authentication with role-based access control, and an inventory ledger that keeps stock honest.

> **Portfolio project.** The name is used for a fictional demo store. It is not affiliated with, or endorsed by, any real supermarket business. All products, prices and customers are made-up demo data, and every illustration is original artwork generated by `scripts/generate-product-images.mjs`.

![Storefront home page](docs/screenshots/01-home.png)

## What it does

**For customers**
- Browse and search the catalogue, filter by category, sort by price, "in stock only"
- Cart drawer with a live free-delivery progress bar, persisted between visits
- Checkout (cash or card on delivery), order confirmation, order history with a live progress timeline
- Cancel an order yourself until it has been packed

**For store staff (Manager and Admin)**
- Dashboard: revenue, orders, average order value, 7-day revenue chart, sales by category, best sellers, low-stock alerts
- Orders: filter by status, search by order number / name / email, move orders through confirm → pack → out for delivery → delivered, or cancel
- Products: create, edit, archive and restore
- Inventory: low-stock list, restock / write-off with a reason, full stock history ("who changed what and why")
- Customers: spend and order counts per customer; Admins can suspend accounts

## Tech stack

| Layer | Choice |
|---|---|
| Frontend | React 19, TypeScript, Vite, React Router (no UI kit: hand-written CSS and SVG charts) |
| Backend | NestJS 11, Node.js 22, REST, OpenAPI/Swagger |
| Database | PostgreSQL 16, TypeORM with explicit SQL migrations |
| Auth | JWT (Passport), bcrypt password hashing, role-based access control (`ADMIN`, `MANAGER`, `CUSTOMER`) |
| Hardening | `class-validator` DTOs (whitelist + reject unknown fields), Helmet, rate limiting |
| Testing | Jest unit tests + Supertest end-to-end tests against a real PostgreSQL |
| Delivery | Docker (multi-stage images), Docker Compose, GitHub Actions CI |

## Architecture

```mermaid
flowchart LR
  Browser["React SPA<br/>(storefront + back office)"] -->|"/api/*  (JWT)"| Nginx["nginx<br/>static files + reverse proxy"]
  Nginx --> API["NestJS API<br/>Auth · RBAC · Validation"]
  API --> PG[("PostgreSQL")]
  subgraph API modules
    direction TB
    M1[auth] --- M2[products / categories]
    M2 --- M3[orders]
    M3 --- M4[inventory]
    M4 --- M5[customers / dashboard]
  end
```

Every request passes three global guards in order: **rate limit → JWT authentication → role check**. Routes are authenticated by default; public ones (catalogue, login, register) opt out with `@Public()`, and staff-only ones opt in with `@Roles(...)`. Secure by default means a forgotten decorator fails closed.

```mermaid
erDiagram

  ORDERS { uuid id PK  int orderSeq  enum status  enum paymentMethod  numeric total }

  STOCK_MOVEMENTS { uuid id PK  int delta  int balanceAfter  enum reason }
```

## Design decisions worth knowing about

- **Stock can never be oversold.** Placing an order runs in one database transaction that takes row locks (`SELECT … FOR UPDATE`) on the products involved, checks stock, decrements it and writes the order. If any line can't be fulfilled, nothing changes. An end-to-end test fires concurrent orders at the last units in stock and asserts exactly the right number succeed.
- **Stock is a ledger, not a number someone edits.** `products.stock` is only ever changed together with an insert into `stock_movements` (`delta`, `balanceAfter`, `reason`, who, note), in the same transaction. Sales, cancellations, restocks and write-offs all use the same code path. The product form deliberately has no "stock" field after creation.
- **Orders snapshot what was sold.** `order_items` stores the product name and unit price at purchase time, so changing a price later never rewrites history. Products that appear on past orders are archived, not deleted.
- **Order lifecycle is a state machine.** Allowed transitions live in one table (`orders/status-flow.ts`), are enforced server-side, and are unit-tested. Cancelling returns reserved stock to the shelf (a `CANCELLATION` ledger row).
- **Authorization is enforced on the server.** The React route guards are a convenience; the API re-checks the role on every call. Customers only ever see their own orders; Managers can view customers but only Admins can suspend them; registration ignores/rejects attempts to set a role.
- **Schema changes are migrations.** `synchronize` is off; the schema evolves through reviewable migration files that run on boot.
- **Money.** `NUMERIC(12,2)` in the database and a rounded helper in code, so totals never show floating-point drift (covered by a unit test).

## Run it

### Option 1: Docker (one command)

```bash
docker compose up --build
```

| What | Where |
|---|---|
| Storefront and back office | http://localhost:8080 |
| API and Swagger docs | http://localhost:3000/api/docs |

The first start runs migrations and loads demo data (38 products, 9 customers, about 78 orders across two weeks). Set `SEED_DEMO_DATA=false` to start empty. For anything public, set a long random `JWT_SECRET` and a real `DB_PASSWORD`.

### Option 2: local development

Needs Node 22+ and a PostgreSQL 16 database.

```bash
# 1. Database
docker run --name sfc-db -e POSTGRES_USER=sfc -e POSTGRES_PASSWORD=sfc_password \
  -e POSTGRES_DB=sampath_food_city -p 5432:5432 -d postgres:16-alpine
docker exec sfc-db createdb -U sfc sampath_food_city_test   # used by the e2e tests

# 2. API  (http://localhost:3000)
cd backend
cp .env.example .env
npm ci
npm run seed          # migrate + demo data (npm run seed -- --reset to start over)
npm run start:dev

# 3. Web  (http://localhost:5173, proxies /api to the API)
cd ../frontend
npm ci
npm run dev
```

## API overview

Interactive documentation is served at `/api/docs`. 25 endpoints:

| Area | Endpoints | Access |
|---|---|---|
| Auth | `POST /auth/register` · `POST /auth/login` · `GET /auth/me` | public / signed in |
| Catalogue | `GET /products` · `GET /products/:id` · `GET /categories` | public |
| Catalogue admin | `GET /products/manage` · `POST/PATCH/DELETE /products` · `POST/PATCH/DELETE /categories` | staff |
| Orders (customer) | `POST /orders` · `GET /orders/my` · `GET /orders/:id` · `POST /orders/:id/cancel` | signed in (own orders only) |
| Orders (staff) | `GET /orders` · `PATCH /orders/:id/status` | staff |
| Inventory | `GET /inventory/low-stock` · `GET /inventory/movements` · `POST /inventory/adjust` | staff |
| Customers | `GET /customers` · `PATCH /customers/:id/active` | staff / admin only |
| Dashboard | `GET /dashboard/summary` | staff |

## Testing

```bash
cd backend
npm test            # 7 unit tests: pricing, order numbers, status workflow
npm run test:e2e    # 10 end-to-end tests against a real PostgreSQL
cd ../frontend && npm run build   # strict TypeScript check + production build
```

The end-to-end suite covers: registration and validation, role escalation attempts, RBAC on every protected area, order totals and stock decrement, atomic rollback of an unfulfillable order, **no overselling under concurrent orders**, customers isolated from each other's orders, the status workflow with restock on cancel, and ledger-backed stock adjustments that refuse negative stock.

## CI/CD and deployment

`.github/workflows/ci.yml` runs on every push and pull request: backend build + unit + e2e tests (against a PostgreSQL service container), frontend type-check + build, and a Docker job that builds the images, starts the whole stack and smoke-tests it through the nginx proxy.

The images are ready to deploy anywhere that runs containers. A natural AWS setup is: images in ECR, the API on ECS Fargate (or App Runner) behind an ALB, the SPA on S3 + CloudFront (or the nginx image), PostgreSQL on RDS, and `JWT_SECRET` / `DATABASE_URL` in Secrets Manager. This repository does not include infrastructure code and has not been deployed.

## Regenerating the screenshots

`scripts/capture-screenshots.cjs` logs in as a customer, shops, checks out, then logs in as an admin and processes that order. It asserts on what appears on screen at each step, so it also works as a smoke test of the full flow.

```bash
npm i --no-save playwright && npx playwright install chromium
node scripts/capture-screenshots.cjs      # needs the API + frontend running and the DB seeded
```

## Known limitations and next steps

- Payments are simulated (cash / card on delivery); no payment provider is integrated.
- The access token is kept in `localStorage` for simplicity. A production version would use short-lived tokens with an httpOnly refresh cookie.
- Product images are referenced by path; there is no upload flow yet.
- No e-mail notifications, delivery slots or customer addresses book.
- Frontend has no automated tests yet; the full flow is covered by the Playwright script above.
